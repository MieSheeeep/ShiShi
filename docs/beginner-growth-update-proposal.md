# 食拾更新方案：新手下厨、做饭记录与成长反馈

日期：2026-11-21  
状态：讨论稿，仅记录更新方案，尚未实现。  
代码核对基线：远端 main `c4448af`，已包含冰箱增强、智能提取和最小部署配置。

## 1. 本次方向

根据用户转述的 11 月 20 日老师建议，下一阶段突出三个关键词：面向新手、增加乐趣、留下做过的菜与成长记录。升级是反馈方式之一，不能代替记录本身。

建议产品定位调整为：**陪新手完成一餐，留下每次尝试，逐渐积累自己的拿手菜。**

核心流程：选一道适合自己的菜 → 跟着做 → 记录这次成果或失手 → 看见成长 → 再做一次。

本轮建议选择“做饭记录＋轻量成长”的方案。仅加勋章和经验条无法补上历史缺失；完整养成游戏需要大量规则、素材和运营，暂不适合作为当前主线。

## 2. 当前基础与明确缺口

已核对当前代码，而非假设项目从零开始：

| 当前已有 | 本次继续利用 | 还缺什么 |
| --- | --- | --- |
| 今天做什么、备料与步骤勾选 | 作为实际下厨入口 | 菜单、进度刷新后恢复，以及完成后的持久记录 |
| 食谱导入、智能提取、核对编辑 | 帮助用户找到并修正做法 | 给新手的难度、关键动作和容易失手之处 |
| 冰箱、找菜、菜单确认、采购 | 帮用户准备这一餐 | 入口需要围绕做饭安排，减少来回管理操作 |
| 首页精选、节气日记 | 提供每日灵感与文化内容 | 与“我今天做了什么”连接 |
| 账号、数据库、图片存储 | 保存个人记录与成品图 | 独立的做饭记录数据与成长计算 |

**关键现状：** `frontend/src/App.vue` 中 `finishCooking()` 当前只清空菜单和步骤并提示开饭，没有将本次制作写入数据库。不能把现有“完成制作”描述成已经支持做饭历史或成就。

已有 V2 食谱与原始快照继续保留；食谱描述“这道菜怎么做”，做饭记录描述“我这一次做了什么”，二者分别保存。

## 3. 第一优先级：每次下厨都留下记录

### 3.1 从下厨开始就有一份草稿

点击“开始做这顿饭”创建账号内的下厨会话，保存所选菜和当时的做法快照。步骤勾选自动保存，刷新或重新登录能继续。进行中的草稿不计算已完成次数。

点击“完成并记录”打开简短收尾页：日期和菜品自动带入，用户只需确认每道菜的结果；拍照、心情和心得都可选。也提供“补记做过的菜”，默认日期由用户确认，注明是补记。

一次做三道菜，保存为一顿饭，内含三条菜品尝试；列表可以按一餐看，也能按某道菜看历次变化。没有下锅的菜标为“本次没做”，不冒充完成。

### 3.2 记录内容

| 内容 | 首版要求 | 用途 |
| --- | --- | --- |
| 做饭日期、菜名 | 必须保存，默认自动带入 | 回看自己什么时候做过什么 |
| 本次结果 | 每道菜确认“做成了 / 还需练习 / 本次没做” | 允许真实记录失手与部分完成 |
| 本次食谱快照 | 后端保存 | 日后原食谱改名或删除仍能读懂旧记录 |
| 我的成品照片 | 可选，自己拍摄或上传 | 形成个人作品墙，不要求拍得好看 |
| 心得、下次调整 | 可选，先提供一个短输入框 | 如“盐少一点”“这次锅太热” |
| 实际耗时、心情 | 可选，后续扩展 | 不让收尾变成填表任务 |

失败也值得记录。不能因为没勾完每一步就禁止保存一次实际尝试；步骤勾选是辅助过程，不是厨艺认证。结果由用户确认，不以照片、AI 评分或打卡截图作为证明。

### 3.3 保存行为必须可靠

- 保存成功后才清理当前下厨状态、展示完成反馈；失败保留草稿和输入，允许重试。
- 同一会话重复点击、重发请求只产生一次完成记录，不重复升级。
- 能编辑心得、照片、日期和结果，误记可撤回；撤回不删除原食谱。
- 记录按账号隔离，自己的作品默认只对自己可见。
- 已完成记录与会话草稿均保存在服务端 SQLite，不以浏览器缓存作为唯一保存位置。
- 照片复用本地图片存储；历史记录中的有效图片不能因为原食谱删除而被一并清理。

## 4. 第二优先级：从记录里看见成长

### 4.1 先做轻量等级，不先做复杂经验经济

建议首版直接按**有效下厨次数**分级，不引入金币、商城或排行榜：

| 等级 | 建议称号 | 累计有效下厨次数 |
| --- | --- | --- |
| 1 | 初入厨房 | 0 |
| 2 | 第一次开火 | 1 |
| 3 | 渐入佳境 | 3 |
| 4 | 家常小能手 | 7 |
| 5 | 我的拿手菜 | 15 |

以上称号与门槛是初始建议，后续按新手试用反馈调整。有效次数按“完成的一餐”统计，至少一道菜确实尝试过；“还需练习”也计入，“本次没做”不计入。一顿三道菜只增加一次下厨次数，三道菜各自的尝试次数仍分别保留。

编辑描述和补传照片不增加次数。补记按用户自报计入，不做客观厨艺认证。撤回后按现有有效记录重新计算等级与勋章，避免数据与展示矛盾。

### 4.2 首批成就少而具体

| 成就 | 建议条件 | 想鼓励的行为 |
| --- | --- | --- |
| 第一次开火 | 保存第一餐实际尝试 | 愿意开始 |
| 再试一次 | 同一道菜出现过“还需练习”，之后再次尝试 | 失手后愿意继续 |
| 我的家常三道 | 尝试过三种不同的菜 | 扩展自己的菜单 |
| 一道拿手菜 | 同一道菜在不同会话中做成三次 | 从会做走向熟练 |

不做断签惩罚，不要求每天做饭，不因未上传照片降低等级。等级表示个人积累，不承诺健康水平或专业厨艺水平。

### 4.3 反馈的样子

完成页用“这顿饭，记下了”作为主反馈，再显示照片、今天做的菜和一句具体变化，例如“你已经尝试了 3 道菜”。首次解锁成就时短暂展示印章或轻动效，允许关闭动效，不反复弹窗。

风格沿用深松绿、暖白、宋体标题和少量朱红，像一份慢慢积累的个人厨房手记。主角是用户做出的菜，不加入复杂游戏界面或沉重的书本装饰。

## 5. 第三优先级：让新手更容易做成

- 首页先给一道低门槛建议：材料较少、动作较简单、现有厨具可完成。耗时与难度只在有来源或用户确认时展示，缺失写“未标注”，不由材料数量直接推断安全或难度。
- 点开做法时清楚列出材料、所需厨具、关键准备；“焯水”“收汁”等术语提供简短解释。
- 跟做时突出当前步骤、已有配图和可选计时，不要求不断切回食谱管理页。实际计时与预计耗时分开。
- 再次做同一道菜时优先提示自己的上次心得，例如“你上次记下：少放一点盐”。这是记录最直接的价值。
- AI 可以解释术语和整理已有步骤，输出要能编辑。涉及生熟、火候等关键事项不凭空生成确定结论；本轮不把自动点评成品照作为验收项。

首版先覆盖少量精选做法的术语说明与提示，不要求一次清洗全库或等采集系统支持所有平台。

## 6. 页面与功能重心调整

首页主区域建议按顺序呈现：

1. 正在做的一餐：有草稿时优先提供“继续做”。
2. 今天试试这道：一道适合新手的做法，直接进入备料与下厨。
3. 最近做过：自己的最新记录、累计尝试与下一个小目标。
4. 节气餐桌：保留节气日记与当季灵感，作为内容支持。

最终导航建议为“首页 / 做饭 / 记录 / 冰箱 / 我的”。菜谱库保留首页固定次级入口和做饭时的选菜入口；采购从本次菜单进入，每周计划放入“我的”或做饭页的次级入口。

“削弱管理”指降低管理操作的展示优先级，保留现有收藏、编辑、标签、批量删除、采购和周计划能力，不删除数据或强制重做。第一阶段先增加记录入口，不同时改完整导航；记录链路跑通后再调整首页与导航，减少集成风险。

## 7. 与节气文化和日常饮食的衔接

把文化内容接到真实行动：用户完成一道当季精选后，可以在自己的记录中保留“这次跟着哪一期做”的出处与日期。逐渐形成“今年立冬，我做了第一碗粥”这样的个人记忆。

首版不扩充养生功效、热量评分或自动健康认证。饮食内容继续以食材搭配、当季背景和已有来源为主。涉及节气的成就可以后续增加，应根据实际选择的精选期次判定，不凭照片或日期猜测。

## 8. 图片来源与评论区问题

群聊里出现了“爬评论区的图片吗”的疑问。这是一个待讨论的图片来源选项，不等于本轮必须接入的需求。

建议首版优先让用户上传自己的成品图；未上传时显示明确标注的食谱封面或占位图，不能把原作者图片、其他人的评论图当成“我的作品”。成品图为空仍可完成记录与成长统计。

豆果/小红书正文与步骤图继续沿用现有采集。评论区图片采集先不列入本轮验收：它不解决个人成长记录的核心缺口，且还需要单独评估平台访问、作者信息和展示方式。若后续用于“大家做出来是什么样”的参考，应独立展示来源，不混入个人记录。

## 9. 数据与接口的建议边界（未实现）

本节供后续成员对齐，不代表 API 已存在；现有接口文档继续描述实际实现。

- 新增账号内下厨会话，包含会话 ID、开始/完成时间、状态、菜品尝试列表、步骤进度及版本号。
- 菜品尝试保留可空的原食谱 ID、菜名/材料/步骤/封面快照、结果、自己的照片、心得。原食谱关联删除后快照仍独立存在。
- 同一道菜的历次练习使用独立保存、不会因原食谱删除而清空的 `dish_key` 关联。补记时可选择已有菜品；手动命名的新菜建立自己的关联，不靠 AI 猜测两道菜是不是同一道。
- 时间统一存 UTC，按上海时区展示日期和分组；用户补记的用餐日期单独保存，不拿服务器接收时间代替。
- 状态为进行中、已完成、已撤回。草稿和撤回不计入等级；有效记录由规则派生，避免单独维护容易失同步的经验余额。
- 首版只读取记录计算成长摘要；是否需要成就缓存，等数据规模和实际性能确定。
- 图片地址复用已有媒体接口与校验，不接受任意站外图片冒充已上传个人作品。

建议新增接口名称：

| 接口草案 | 职责 |
| --- | --- |
| `POST /api/cooking-sessions` | 创建草稿，接收客户端生成的唯一请求 ID |
| `GET /api/cooking-sessions` | 分页读取进行中与历史记录，可按菜品/日期筛选 |
| `GET /api/cooking-sessions/{id}` | 读取自己的草稿或历史详情 |
| `PATCH /api/cooking-sessions/{id}` | 保存进度、心得、照片和结果，版本冲突返回 409，保留本地输入待重试 |
| `POST /api/cooking-sessions/{id}/complete` | 同一事务内确认结果并完成，重复请求返回同一记录，不重复计数 |
| `POST /api/cooking-sessions/{id}/withdraw` | 撤回误记，重新派生成长摘要 |
| `GET /api/cooking-summary` | 返回有效餐次、尝试菜数、等级与成就 |

照片上传成功但保存记录失败时保留表单与已上传地址以便重试。第一阶段不自动清理未关联图片，后续媒体清理必须同时考虑食谱与做饭记录的引用。

正式开发先将一个固定完整样例放进仓库，前端可用样例开发，后端、内容和提取模块同时进行，不要求所有人等待一整套新接口完成。

## 10. 实施顺序与并行分工

### 第一批：必须先把记录做实

完成服务端草稿、完成保存、历史列表、详情、编辑与撤回；完成页先显示记录成功和累计次数。第一批不依赖等级动画、评论图、全站新导航或新的模型能力。

### 第二批：成长与新手体验

接入五档等级和首批四个成就，增加上次心得提示；完善少量新手精选的术语与关键步骤；首页加入继续下厨、最近记录和小目标，再调整导航。

### 第三批：按试用结果扩展

再评估成品作品墙筛选、同一道菜的变化对比、节气主题成就和可导出的个人做饭回顾。多人社区、排名、虚拟货币和评论区图片采集不进入前两批。

## 11. 必须验收的场景

1. 一餐包含三道菜，两道尝试、一道人为跳过：保存一餐，两条实际尝试；未做的菜不计菜数。
2. 保存失败后菜单、勾选、心得和照片仍在，重试成功只生成一份完成记录。
3. 刷新、退出再登录仍能找到进行中的草稿及已完成记录，跨账号不可读写。
4. 原食谱改名、重排或删除，历史仍显示当时的做法和自己的照片、心得。
5. 一次没做好的尝试可以保存；再次做这道菜能看到旧心得，满足规则时解锁“再试一次”。
6. 同一会话重复完成、补传照片和修改心得不重复计数；撤回后统计、等级与成就一致更新。
7. 一餐三道菜不等于三次下厨，三个不同会话做同一道菜才能累积其练习次数。
8. 不上传照片、不填心得，也能完成基本记录；不误把示例图标为用户成品。
9. 电脑和手机都能完成“选菜—跟做—记录—回看”，库存、采购、AI、周计划原有功能仍可进入。
10. 备份恢复后，个人记录、照片引用和成长摘要仍一致；测试使用临时数据，不修改正式库存。

## 12. 评估是否改对了方向

先邀请少量做饭经验较少的同学走一遍流程，观察能否独立选菜、跟做、保存并找到上次记录。记录卡住的位置与实际反馈，不预先假定成就系统一定有效。

关注：开始下厨后保存记录的比例、保存失败/重试情况、第一次尝试到第二次尝试的变化，以及用户是否主动查看自己的心得。统计需明确草稿、实际尝试和撤回的口径；首版可在测试环境手工整理，不先做用户行为追踪系统。

对外汇报可概括为：**在已有食谱和库存能力上，把重点转向新手完成一餐的体验；用真实下厨记录承载作品、复盘和成长，让用户看见自己从第一次尝试到逐渐熟练的过程。**
