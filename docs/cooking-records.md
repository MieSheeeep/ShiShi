# 下厨会话、厨房足迹与成长记录

本轮依据[修正案 R2](beginner-growth-update-proposal.md)开发。服务端记录与成长接口已实现；页面接入及实际验收结果见[验证记录](verification.md)。

## 页面使用

主导航为首页、按食材搜菜、厨房闯关、下厨记录。首页保留节气日历推荐与菜谱管理（导入食谱、搜索、标签筛选、菜谱卡片与选菜）；菜单与采购清单通过选菜浮条进入，账号管理与 AI 设置留在侧栏底部。

1. 在首页菜谱库或按食材搜菜中选菜，点「去做饭」创建服务器草稿；也可在厨房闯关或下厨记录页补记。补记时可手写菜名，也可点「从食谱中选择」挑一道自己的食谱，按所选日期带着这份材料与步骤进入记录，之后仍会按该菜品累计尝试次数。
2. 在「厨房闯关」页可查看当前阶段与挑战卡（第一次开火、再试一次、三道家常菜、练成拿手菜、冰箱清库存实战），已通关卡片可直接回看触发记录；进入做饭后按快照备料、勾选步骤并随操作自动保存。
3. 切到「收尾留念」，逐菜选择做成了、还想再练或这次没做；自己的成品图和心得均可跳过。
4. 点「留下这一餐」，服务端确认成功后才出现留印反馈。确认过程中暂时锁定编辑，失败后保留草稿并恢复编辑。
5. 在「下厨记录」页可切换「食光月历」（按月查看开火日与当天每餐记录、按日补记）和「拿手菜与进化史」（按熟练度筛选、展开同一道菜的历次变化时间轴），打开一餐可修改、撤回或再次开做；再次做会在跟做前提示真实的上次心得。

保存请求按版本串行执行。失败字段会随后续保存一起提交，也可手动重试；延迟旧响应不能降低已保存版本。409 冲突保留输入，需明确选择恢复服务端版本（放弃本次输入）或保留输入重试。新账号不预填历史，没拍照的尝试使用文字作品卡。

## 一餐和一道菜

一次会话代表一顿饭，包含最多 20 道菜。每道菜保存当时完整食谱快照、稳定菜品身份、步骤进度、本次结果、自己的成品图和心得。原食谱修改或删除不覆盖历史。

`pending` 为尚未确认，`success` 为做成了，`practice` 为还需练习，`skipped` 为本次没做。完成时必须逐菜确认且至少一道实际尝试；不要求勾完所有步骤。完成一餐只增加一次有效餐次，菜数按不同菜品身份统计；失手的实际尝试也计入，没做的不计入。

会话状态为 `in_progress`、`completed`、`withdrawn`。草稿与撤回记录不计入成长；撤回后不能把同一会话重新完成，需要另开一餐。编号按账号递增，撤回不会给其他记录重新编号。

## 接口与保存

所有接口使用现有 Bearer 鉴权，别人的记录和菜品身份返回 404。

| 方法 | 路径 | 请求或说明 |
| --- | --- | --- |
| POST | `/api/cooking-sessions` | UUID `client_id`，`recipe_ids` 或 `manual_name` 二选一；可选 `cooked_on`、`meal_slot`，补记/再练可带本人 `dish_key` |
| GET | `/api/cooking-sessions` | 查询 `state`、`month=YYYY-MM`、`dish_key`、`page`、`page_size`，返回 `{items,total,page,page_size}` |
| GET | `/api/cooking-sessions/{id}` | 读取自己的会话，包括历史快照 |
| PATCH | `/api/cooking-sessions/{id}` | `version` 必填，可修改 `cooked_on`、`meal_slot`、`title`、`note`、`dishes` |
| POST | `/api/cooking-sessions/{id}/complete` | `{version}`，保存完成，重复完成返回同一记录 |
| POST | `/api/cooking-sessions/{id}/withdraw` | `{version}`，撤回，重复撤回幂等 |
| GET | `/api/cooking-summary` | 有效餐次、不同菜数、段位、本机百分位、印章和拿手菜聚合，字段见下 |

`/api/cooking-summary` 返回 `{meals, dishes, level, percentile, achievements, repertoire}`：`level` 含 `number`（1–8）、`tier`（`bronze`/`silver`/`gold`/`platinum`/`diamond`/`star`/`king`/`peak`）、`title`、`star`（档内星级，巅峰档无上限）、`next_at`（下一档门槛餐次，巅峰为 `null`）、`remaining`（距下一档还差几餐）；`percentile` 含 `percent`（本机超过的账号百分比）、`accounts`（本机账号数）、`ahead`（有效餐次更少的账号数），只在本机 SQLite 内比较。

| PUT | `/api/cooking-dishes` | `{dish_key,status}`，手动标记 `tried`、`practice` 或 `signature` |

创建时食谱快照由后端读取当前账号的食谱，不能提交任意用户的食谱编号。手动补记必须填写非空菜名，不能同时提供食谱列表。重复 client_id 在该账号下返回已经创建的记录，网络重试不会另建一餐。

PATCH 的 dishes 为局部更新数组，每项 id 必须属于本会话，只接受 `outcome`、`note`、`photos`、`completed_steps`。不能插入新菜、改快照或伪造步骤 ID，未知及重复 ID 拒绝。已完成记录改结果仍必须保留至少一次实际尝试；误记使用撤回。

每次写入递增 version，使用旧版本返回 409，避免另一个窗口覆盖更改。创建、版本检查、完成和撤回均在事务内完成，失败不留下半条记录。用户应保留冲突时尚未保存的输入，确认当前记录后再操作。

分页默认每页 12 条，最多 50，按用餐日期与 ID 倒序；不指定状态时排除撤回。日期严格校验真实的 YYYY-MM-DD，默认上海当天，补记不能选未来日期；开始、完成和更新时间存 UTC。title 最多 80 字，心得最多 1000 字，每道菜最多 12 张成品图。

业务错误使用中文 `detail`。字段验证错误沿用当前项目的 Pydantic 422 结构，调用方需展示可理解的输入提示；不能把保存失败当成成功完成。

## 餐点

每条会话可选一个 `meal_slot`，取值固定为 `breakfast`、`lunch`、`teatime`、`dinner`、`supper`，对应早饭、午饭、下午茶、晚饭、夜宵；不传时保存为空字符串，表示未标注。该字段只描述这一餐属于哪个时段，不参与有效餐次、菜品计数和段位计算，历史记录保持未标注。

前端新建记录时按当前时间预选（5–10 点早饭、10–14 点午饭、14–17 点下午茶、17–21 点晚饭、其余夜宵），用户可改；补记同一表单内也可选。下厨记录按日期查看时，同一天内按上述顺序分区展示，只显示有记录的分区，未标注的排在最后。餐点取值与默认时间段定义在 `frontend/src/mealSlots.js`，与后端 `cooking_schema.py` 的 `MealSlot` 必须同步。

## 菜品身份和图片来源

`dish_key` 是前端不可解析的不透明字符串。服务端为当前食谱实例随机分配身份，独立保存于 `cooking_recipe_instances`。修改原食谱继续使用原身份；删除原食谱只清当前映射，历史快照与身份仍保留，新菜即使复用了旧整数 ID 也有新身份。客户端指定相同 created_at 不能冒充原实例。

`POST /api/media` 沿用原上传方式，同时登记当前账号的上传归属；只有已登记且文件存在的本人 `/api/media/` 地址才能保存为成品图。参考封面、精选图和他人的地址不能直接当个人作品。功能启用前没有登记归属的旧图片，作为成品图使用时须重新上传；不猜测历史上传人。

目前媒体读取仍沿用原内容哈希 URL 的公开访问方式，记录列表和详情按账号鉴权。这不是新增公开作品广场，也不提供带权限校验的私密图片下载。图片不进行自动物理清理，原食谱删除不会删除记录照片。

## 成长规则

| 段位 | 称号 | 有效餐次 | 每档星级 |
| --- | --- | --- | --- |
| 1 | 倔强青铜 | 0 | 每 2 餐一星，每档 3 星 |
| 2 | 秩序白银 | 6 | 同上 |
| 3 | 荣耀黄金 | 12 | 同上 |
| 4 | 尊贵铂金 | 18 | 同上 |
| 5 | 永恒钻石 | 24 | 同上 |
| 6 | 至尊星耀 | 30 | 同上 |
| 7 | 最强王者 | 36 | 同上 |
| 8 | 巅峰 | 48 | 星数无上限，每 2 餐一星 |

账号面板的「账号管理」页用渐变字牌显示当前段位与星级，展示距下一档的进度，并可展开查看全部段位、门槛与升级规则；卡片同时显示「本机超过 X% 的账号」——该百分比只在本机 SQLite 的账号之间比较，只有一个账号时显示暂无可比较。前端展示表在 `frontend/src/cookingLevels.js`，实际计算在后端 `backend/cooking_store.py` 的 `TIERS` 与 `STAR_STEP`，改档位或门槛时两处必须同步。

首批印章：第一次开火（第一餐）；再试一次（同菜失手后在另一餐再尝试）；三道家常菜（三种菜）；我的拿手菜（同菜三个会话做成）。每枚印章保留触发会话 ID 和完成时间，可回到那一餐。

成长根据现有有效记录派生，按真实完成时间和 ID 判断尝试先后，补记日期不改写实际完成顺序。修改心得、补照片、重复完成都不重复计数；修改结果或撤回后重新计算。拿手菜的手动标记与自动成就分别保存，不自动颁发“做成三次”成就。

## 存储、升级和备份

新增四张表：`cooking_sessions` 保存会话和 JSON 快照，`cooking_dishes` 保存手动状态，`cooking_uploads` 保存上传归属，`cooking_recipe_instances` 保存当前食谱实例身份。不替换现有食谱、库存或采购数据。用户注销时，SQLite 触发器在原账号删除事务内清理这些账号数据。

数据库升级只增加表和触发器，仍应在升级真实数据前备份数据库与 `data/media/`。运行中 SQLite 使用在线备份方法；仅复制运行中的主文件可能漏掉 WAL 内容。恢复时停止服务，恢复数据库与媒体，并使用对应程序版本。只备份数据库不能保留照片文件。

开发和界面验收使用独立临时数据库。产品不会给新账号自动填入假的下厨记录，展示样例不能写入真实用户历史。月度回顾导出、社区和评论区图片采集尚不在本轮交付范围。
